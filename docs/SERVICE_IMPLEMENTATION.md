# Service form implementation

All 47 catalog services have executable, versioned demonstration application schemas. Every service has a valid synthetic sample and server-compatible validation; the application service, authorization, approval, issuance, credit ledger, and verification modules consume the same contract. Operational availability describes this independently implemented application, not the reference website or legal authority to issue an official certificate.

The reference audit remains Phase 0 evidence. No new live reference audit was performed. The sanitized 47-service / 48-entry-form metadata remains unchanged and can still be rendered separately through `getCatalogPreviewSchema(serviceNo)`.

## Contract and versioning

- `getServiceSchema(serviceNo)` returns the latest immutable operational schema for any service number 1–47; an explicit version returns its preserved historical contract.
- `operationalServiceNumbers` contains every number 1–47 exactly once. `operationalSchemas` contains one currently enabled version for each service: #45 remains v1; the other 46 services use v2. `allServiceSchemaVersions` contains all 93 published versions for database bootstrap.
- `demoPayloads[serviceNo]` is frozen synthetic data. `getDemoPayload(serviceNo)` creates a mutable, isolated copy for a new demonstration application. Samples never contain captured reference values, real identity numbers, authentication data, or fabricated attachment handles.
- `validateServicePayload(serviceNo, payload, version)` validates required fields, object types, unknown and inactive fields, enums, Unicode lengths, strict ISO calendar dates, numeric ranges, integer constraints, repeatable rows, and private attachment metadata. Tenant, applicant, attachment ownership, status, authority, subscription, and payment checks belong to the backend.
- Family #2, trade #42, and permanent resident #45 retain their published v1 canonical hashes. Existing applications continue to use their pinned versions. An early v1 release of the expanded 44 forms was already persisted in tested applications before final publication. Its exact schema objects are retained in `expanded-v1-schemas.json`; finalized forms are published as v2. Trade v2 extends the immutable v1 with all 37 observed field mappings. Family v2 likewise maps all 20 observed fields within its existing member array. Changing any persisted contract later requires another version.

## Evidence boundaries

`reference-catalog.json` preserves safe metadata: field names, labels, HTML input type/required/maxlength/accept flags, repeated-control information, group identifiers and entry-path descriptions. Source hidden inputs, public route descriptions and payment UI metadata are evidence, not executable backend contracts.

Across all 47 current service schemas, every observed service-specific visible field is represented in the operational schema's evidence mapping. Repeated arrays become ordered objects: `heirs[]`, `corrections[]`, or `supporting_documents[]`. A field's evidence status is `inferred` when the observed field presence informs an independently implemented shape. Additional facts and common purpose/language/declaration fields are `proposed`. Operational dropdown choices, required flags, numeric bounds, conditional behavior, and cross-field checks are all independently proposed. They are not claims about the source server's validation or official domain policy.

The mapping reconciles **340 service-specific field occurrences across 47 services**, representing **206 distinct field names**. The other **11 of the original 217 distinct data-field names** are common checkout/address controls handled through the independent application, tenant, language and billing workflow. This is field-purpose coverage; it is not evidence of identical source dropdown values, validation or downstream behavior.

The prior #2, #42, #45 v1 schemas remain intentionally stable, including their original independently selected field subsets. All initial fields remain inspectable in the reference preview. Trade v2 maps all 37 captured entry/renewal fields while preserving v1 payload compatibility. Added business, proprietor, geographic, tax-reference and capital fields are optional under independent demo policy. Family v2 also maps all 20 observed fields, extending its existing member rows with optional identity, father and comment fields and its household section with parent/spouse, death date and registration facts. Old valid family payloads remain valid in v2.

Common source checkout fields are replaced by independently controlled application context: applicant/profile, applicable address selection, purpose, language, confirmation, tenant derived from the session, and backend billing/approval. No applicant-provided office ID, price, coupon, source token or approval status can override backend authority or fees. Coupon fulfillment, official geographic directory lookup, official urgency/delivery policy, and live payment gateways are not implied by the form schemas.

## Validation and security details

- Repeatable heir/related-person lists require 1–30 rows. Minor status requires a guardian and rejects inactive adult identity-reference data. Supporting documents allow at most 5 rows; a supplied row requires its description/type and a real uploaded file handle.
- Correction lists require 1–30 rows. Each category is unique within the application and the corrected string must differ from the existing string after trimming.
- Private attachments accept the existing `{attachmentId, mimeType, byteLength}` shape, PDF/PNG/JPEG, and at most 2 MiB. The schema cannot certify a file as safe or grant permission to another user's upload. The backend remains responsible for file verification and access checks.
- License geography inputs are demo names/references. They intentionally do not invent a government directory or official codes. Changing the address category requires clearing stale values from inactive branches.
- Names and descriptions use bounded Unicode-aware lengths. Income, capital, assets/liabilities and vehicle measurements use finite nonnegative numbers with explicit upper bounds. Ward and holding year use integer constraints. Dates reject invalid calendar days.
- Unknown properties are rejected recursively, including caller-supplied tenant, approval or price claims. All published schema objects and fixtures are recursively frozen.
- Required flags and allowed options are demo policy. They require domain-owner review before official operation. The original source's successful submission/approval/payment/document paths remain unverified.

## Verification

`npm run test:forms` passes **72 tests**: the original 14 regressions, 47 individually named service cases, and 11 focused cross-service cases. Each service case verifies a valid synthetic payload, rejected empty form, missing required fact, wrong primitive/row type, rejected untrusted tenant/approval/price claims, required declaration, immutable fields and bilingual labels.

Focused cases verify exact original schema hashes, 93 immutable version identities, all 37 trade and 20 family field mappings and expanded validation, sample isolation, complete newly enabled observed-field mappings, minor guardian/row limits, correction integrity, conditional personal information, exclusive license geography, finite/bounded numbers, integer year, invalid dates, and private attachment metadata. Backend persistence, approval, billing, certificate generation and browser journeys are verified by their respective integration suites; this document does not count schema tests as end-to-end tests.

## Remaining domain work

The schemas make all catalog applications executable, but do not establish official eligibility, certificate wording, legal validity, government-system connectivity, all reference administrator features, live prices or gateway behavior. The next domain milestone is approval of jurisdiction-specific schemas/templates and integration adapters, especially inheritance shares, identity checks, official registers, tax assessments, license renewal rules, document requirements and geographic directories. Schema updates must be versioned and applications already approved must retain their original payload/template versions.
