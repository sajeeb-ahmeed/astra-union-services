# Bangladesh geography integration

The supplied rural geography dataset is integrated as shared PostgreSQL reference data. Registration, office onboarding/profile and the public office directory use parent-linked selection instead of arbitrary location text. A location record does not establish an operational office or its official authority.

## Supplied coverage and independent checks

| Level | Records | Parent | Qualification |
|---|---:|---|---|
| Division | 8 | None | Community dataset identifiers |
| District | 64 | Division | Bilingual names |
| Upazila | 495 | District | `upa-388` (Shaistaganj) has no supplied unions |
| Union | 4,586 | Upazila | Source compilation removed 13 exact bilingual duplicates |
| Union ward | 41,274 | Union | Nine derived numbered wards per retained union |

The five JSON arrays contain **46,427 records**. Independent automated checks verify strict UTF-8 decoding/round-trip, no BOM, NFC strings, nonempty trimmed fields, exact expected schemas, unique identifiers, all parent references, per-union ward counts and deterministic ward identifiers. SHA-256 values match the supplied validation report. Results are written to `execution/geography-dataset-validation.json` by `apps/web/test/geography.test.ts`.

The independent result is **PASS WITH WARNINGS**, not certification that the supplied data is a current official national register. The source is `bangladesh-geo-data@4.0.9`, as documented by the supplied compilation. Its source notes cite a nine-ward rule; this integration checks that derivation consistently without asserting a fresh legal verification. Original README, source notes, validation report, changelog and MIT license remain in `data/geo/`.

Known coverage limits:

- IDs such as `div-01` and `uni-0001` are dataset/application identifiers, not BBS codes.
- Municipality and city-corporation wards require a separate urban hierarchy and are absent.
- Shaistaganj has an explicit empty union list. The UI shows that gap and does not invent children.
- Some distinct source IDs have the same name within a parent. Both Bengali and English names are retained; IDs remain the identity key.
- Derived ward numbers do not describe surveyed boundaries, villages or a gazetted ward assignment. The user must confirm the applicable ward with their office.
- Data validation checks the supplied package, not changes in administrative boundaries after its documented preparation date.

## Public lookup contract

All routes are under `/api/v1`. Lookups return `{items, total, parentCode}`; items include `code`, `nameEn`, `nameBn` and `parentCode`. The division response has no required parent. A child endpoint requires the immediate parent code.

| GET route | Required query | Purpose |
|---|---|---|
| `/geography/metadata` | None | Counts, scope, derivation and identifier limitations |
| `/geography/divisions` | None | Eight available divisions |
| `/geography/districts` | `parentCode=div-01` | Districts in one division |
| `/geography/upazilas` | `parentCode=dis-01` | Upazilas in one district |
| `/geography/unions` | `parentCode=upa-001` | Unions in one upazila |
| `/geography/wards` | `parentCode=uni-0001` | Nine derived wards in one union |

Missing or malformed query parameters return HTTP 400; syntactically valid but nonexistent or wrong-level parents return 404. A valid parent with no children returns 200 and an empty list. Child requests are bounded to one parent: the frontend never downloads 41,274 ward records to render a selector.

The office directory accepts `divisionCode`, `districtCode`, `upazilaCode` and `unionCode` filters. These select registered participating offices; an empty result does not mean that a geographic place does not exist. Legacy office text remains available until that office is deliberately mapped to a source record.

## Registration and administrative behavior

The web registration form collects a complete division → district → upazila → union → ward chain, then a participating office. Changing a parent immediately clears its descendants. Controls provide loading, unavailable-data and retry states. Cached child lookups are keyed by the parent code, with bounded client storage; stale in-flight responses cannot replace the newly selected parent's options.

New geographic values travel as a `geography` object with `divisionCode`, `districtCode`, `upazilaCode`, `unionCode` and `wardCode`. The backend checks their actual parent relationships before storing them; client controls are not treated as an authorization or validation boundary. An internal account reference can be generated by the server, so registration no longer requires the citizen to invent a synthetic identifier.

Geography reference data is public and shared. Citizen/office records retain tenant ownership and existing role authorization. Geographic selection does not grant an approver role, change an office's authority, enroll an unregistered office or establish a person's identity.

## Reproducible verification

Run the existing development database initialization/migration workflow before browser/API tests. Then run:

```sh
npm run typecheck
npm run test:api
npm run test:web
```

The geography source-only test can run without a server:

```sh
node --import tsx --test --test-name-pattern="geography source" apps/web/test/geography.test.ts
```

After authorized deployment, run the read-only verifier:

```sh
ASTRA_LIVE_URL=https://astra-union-services.onrender.com npx tsx scripts/verify-hosted-geography.ts
```

On PowerShell, set `$env:ASTRA_LIVE_URL` before executing the script. It performs only unauthenticated GET requests, checks metadata, all 8 division/64 district records, a complete child path in each division, invalid parents, the known coverage gap and directory filtering. It records results in `execution/geography-hosted-qa.json`. It deliberately distinguishes representative hosted checks from exhaustive validation of all supplied file records.

## Production boundaries

The real PostgreSQL workflows, tenant isolation, PDF/QR issuance and exactly-once credit accounting remain functional. This geography integration does not activate government identity verification, official signing authority, live payment collection, outgoing email/SMS or urban administrative coverage. Certificate and payment disclosures remain visible where they affect decisions. Real citizen-data operation still requires the relevant operating authority, privacy/retention policy, reliable hosting/backups and configured providers; the current Render free database remains time-limited as documented in `HOSTED_DEPLOYMENT.md`.
