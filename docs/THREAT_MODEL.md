# Astra threat model and security boundaries

Updated for **0.8 live and verified**. The controls below have local/CI and scoped hosted acceptance. See [release 0.8](RELEASE_0_8.md) and [hosted deployment](HOSTED_DEPLOYMENT.md) for exact scope and runtime. Passing those checks does not close the residual production gates.

This is not a penetration-test certification or legal-compliance determination. The reference audit did not establish private server/database details or successful official issuance/payment behavior. Those evidence limits remain unchanged.

## Assets and trust boundaries

Protected assets include passwords, session/recovery/challenge tokens, authenticator seeds and recovery-code hashes, citizen records, application history/private uploads, approval grants, certificate/print PDFs, QR tokens, fees, subscriptions/wallet/ledger, gateway secrets and backups. Tests use synthetic fixtures. Original private audit material is excluded from the app and source delivery.

Browser input is untrusted. The API derives account/tenant context and checks role, state and ownership. Forced RLS supplements that trusted context. Ordinary users never receive database credentials; a compromised service credential can set another account or tenant context, so RLS is not a defense against full service compromise. The runtime role is `NOSUPERUSER NOBYPASSRLS`, cannot inherit the migration owner, and cannot directly update the wallet balance.

The managed migration owner also lacks superuser/RLS-bypass privileges. The new recovery exporter therefore enumerates validated tenant/account scopes inside one read-only snapshot instead of disabling RLS or widening runtime access. Its separate local recovery-cluster operator has elevated loading privileges only in that isolated environment. Restored application and object-owner roles receive fresh credentials and restricted attributes; source role memberships/passwords are not recreated.

Local Chromium is a separate renderer. Public `SECURITY DEFINER` functions expose narrow projections with fixed search paths and restricted execution. Citizen gateway payments and synthetic SaaS settlement are separate trust boundaries. Merchant collection remains disabled, and no real provider transaction is established by mock tests.

Software ownership does not authorize unrestricted citizen access. Lawful processing, retention, hosting and official authority must be settled by the responsible parties before real data or official issuance.

## Identity and official use

Signup/staff registration creates `SYNTHETIC_DEMO` profiles with demonstration references. Calendar-valid dates, self-entered service facts and uploads are not identity verification. No lawful NID/BRN/OTP provider, biometric check, legally appointed signatory or official certificate integration is configured. Offices/plans remain demo-constrained and PDFs say **DEMO / NOT OFFICIAL**.

All 47 services have independent operational demonstration workflows. Domain owners must still approve eligibility, sensitive fields, guardianship, templates, appointment authority, statutory fees, disclosure and expiry. An administrator's demonstration grant or passing test does not establish official authority or prove parity with unknown reference-site behavior.

No jurisdiction-specific retention duration is invented. Append-only history protects integrity but does not implement governed erasure. Tenant export/closure remains a separate scoped workflow; the operational all-database recovery tool is not a tenant-facing citizen-export feature.

## Encryption and privileged operations

Passwords/token hashes do not encrypt profiles or document bytes. Existing hosted HTTPS and verified database transport do not establish application field encryption or independent backup-key custody. Configure deployment secrets separately from the source repository; ignored runtime files are workstation conveniences, not a managed secret store.

The 0.8 managed recovery archive uses authenticated AES-256-GCM. Its archive key is outside the workspace and backup directory, but both locations are on this workstation: that is **not independent key custody or offsite replication**. The exporter keeps source credentials out of archive metadata and public evidence. Actual document rows, password hashes and session data inside the encrypted archive remain sensitive. File-mode flags alone do not prove Windows ACL restrictions.

Restore creates fresh restricted roles on a separate loopback cluster, preserves application object ownership and verifies RLS/grants/ledger/PDF state. It does not recreate provider memberships or reuse database passwords. Direct SQL verification is not proof that the complete recovered application, its matching MFA key and operational services are ready for cutover. No approved paid-hosting purchase or long-term hosting solution is implied.

Migration 014 validates that every tenant audit event has a tenant, including rows hidden by forced RLS. A hidden legacy NULL causes failure; no audit row is rewritten or silently discarded. Global owner/account security history belongs in the new account-scoped table.

## Deployment and release gates

Production startup enforces an exact HTTPS origin, restricted runtime database URL and a unique synthetic-webhook secret. Proxy trust accepts an explicitly configured literal IP and optional loopback. Mixed-case authentication routes receive the same general rate-limit treatment. Docker/Linux CI and HTTPS Render deployment are established release history, and 0.8 has separate exact-runtime hosted acceptance evidence.

After any account enrolls in MFA, do not roll back to the password-only runtime in 0.7 or earlier: that application ignores enrolled MFA state and would accept the password alone. Roll forward or deploy an explicitly compatible MFA-aware build. Retain migrations 013/014, their data and the matching MFA encryption key; automatic downgrade or silent factor disablement is not an acceptable recovery path.

Before real office use, complete the [documented backlog](DELIVERY_BACKLOG.md): protected hosted preservation and independent recovery, offsite/key custody and durable hosting; privileged recovery/access review; file quarantine/scanning; monitoring/shared throttling and recurring backups; capacity/accessibility/pilot acceptance; lawful identity, official rules/templates and signatories. Payment merchant work remains deferred at the owner's direction.

The commissioning user owns the independent source. Third-party dependencies/fonts retain their licenses. Private reference code, government marks and captured citizen values are excluded.


## 0.9 attachment boundary

Uploads enter quarantine and remain private until an exact immutable hash has a trusted fresh-engine scan. Pending/error/rejected bytes cannot be downloaded or used for submission, approval or new issuance. A separately authenticated service lease, tenant RLS, immutable append-only results and final issuance locks defend against cross-tenant handles, stale/replayed verdicts and PDF-generation races. The scanner credential is intentionally privileged over queued uploads across active tenants; keep it outside source/browser state and rotate on compromise. The selected Windows PC is part of the trusted processing environment, and ClamD can spool private temporary files. Malware signatures do not detect every unknown threat; clean is not a universal safety guarantee. PC outage fails closed. Retention/disposal, always-on hosting, independent key custody and offsite backup remain policy/infrastructure decisions. See [runbook](ATTACHMENT_SCANNER_RUNTIME.md) and [release notes](RELEASE_0_9.md).
